# Адверсариальное ревью и оптимизация DS5Link 0.1.28

Дата: 2026-11-03. База: корневой commit `40512d4`, текущий локальный Windows-движок, патч `patches/vds/0001-ds5link-bootstrap.patch`, пакет `artifacts/releases/DS5Link-0.1.28`. Движок закреплён на upstream `ec531599dfdd02e14ce68efd8c0d2dcb439894a5` с локальными изменениями. Reverse-check патча проходит. Это новое ревью текущей версии, а не переоценка старого отчёта 0.1.4.

Найдено 6 замечаний: один P1 и пять P2. Два дефекта воспроизведены изолированным managed-probe; для остальных ниже явно указаны статические доказательства и измерения. Продуктовый код, установленная программа, драйверы и настройки не изменялись. Пробные сборки и результаты сохранены в `artifacts/review-20261103`.

## Находки

### R1. P1 — зависшая Bluetooth-запись может навсегда остановить PS5-сессию без автоматического восстановления

Места: `engine/vds/src/platform/win32/vdsd.cc:783–795, 1409–1440, 2244–2271, 2883–2887`; `engine/vds/src/platform/win32/vds_bt.cc:539–540, 748–754`.

`send_bt_state_if_changed` держит `BridgeState::mutex`, затем `bluetooth_mutex` во время синхронного `write_interrupt_packet`. Этот вызов ждёт опустошения выходной очереди без срока ожидания; фактический overlapped WriteFile также ожидается с `INFINITE`. Если запись не завершается, поток обработки входа после очередного отчёта останавливается на `state.mutex`. Тайм-аут следующего HID-чтения уже не помогает: до следующего чтения выполнение не доходит.

Supervisor проверяет только полное отсутствие первого входного пакета (`last_input == time_point{}`), а не устаревание уже полученного ввода. Его собственный heartbeat и IPC при этом могут оставаться исправными, поэтому watchdog не запускает восстановление. Состояние уйдёт из Active в Connecting и может остаться там. Даже явная пауза сначала заставляет stop-monitor ждать тот же `bluetooth_mutex` перед отменой I/O; в этом случае остаётся аварийный перезапуск через контроль длительного завершения worker.

Доказательство: статическая цепочка ожиданий в текущем коде. Зависание физического Windows-драйвера не инжектировалось; это не утверждение о наблюдавшемся зависании на данном ПК.

Исправление: ограничить время выходной операции и ожидания очереди; отменять транспорт независимо от mutex отправки; проверять возраст последнего ввода в работающей PS5-сессии. Передача output через одного владельца с номером поколения позволит сохранить порядок игровых и ручных команд без длительного удержания общего mutex.

Приёмка: транспорт-имитатор принимает первый input, затем никогда не завершает output. Автоматическое восстановление должно сработать без команды pause; pause/stop должны завершаться в установленный срок с корректной судьбой HidHide-журнала.

### R2. P2 — захват «звук → haptics» не восстанавливается после ошибки старта или остановки аудиоустройства

Места: `src/DS5Link.App/EffectsRuntime.cs:13–16`; `src/DS5Link.App/AudioReactiveCapture.cs:65–76`.

`AudioReactiveCapture.Start` перехватывает ошибку и возвращает управление без запущенного capture. Вызывающий код безусловно присваивает `audioRunning=true`. Следующие `SyncAudioEffects` при том же активном контроллере пропускают повторный запуск. `RecordingStopped` также не сбрасывает этот внешний флаг. Временная недоступность выбранного устройства может оставить звуковую отдачу выключенной до переключения настройки, сессии или перезапуска UI.

Воспроизведено на настоящих классах с заведомо несуществующим endpoint ID, без открытия реального аудиопотока: `running=true`, `captureMissing=true`, повторный `SyncAudioEffects` не вызвал Start. Результат: `artifacts/review-20261103/probe-result.txt`.

Отдельное ограничение того же lifecycle: режим «Устройство вывода Windows» разрешает default endpoint только при Start; подписки на смену устройства нет. Смена default output не переключает существующий capture автоматически.

Исправление: возвращать результат Start или предоставлять фактический статус capture, сообщать об остановке, повторять запуск с ограниченной задержкой. Для default-режима отслеживать смену endpoint. Приёмка: неуспешный старт → устройство снова доступно; unplug/replug; смена default output без переподключения геймпада.

### R3. P2 — неудавшееся автоприменение теряет несохранённую настройку

Места: `src/DS5Link.App/SettingsAutoApply.cs:17, 41–52`.

`LatestSettingsApplier.Run` удаляет запись из pending до `await apply`. При ошибке IPC или временно занятом MainWindow запись теряется. После сообщения об ошибке `HasPending=false`; повторный Flush успешно завершается без применения. Закрытие окна не обнаруживает оставшийся несохранённый draft, поскольку проверяет только очередь и выполняющуюся задачу.

Воспроизведено с однократной ошибкой делегата: `calls=1`, `pendingAfterFailure=false`, второй Flush успешен. Данные: `probe-result.txt`. Это не требует отказа железа.

Исправление: сохранять dirty/error-состояние до подтверждённого успеха, не затирать более свежую настройку неудавшейся старой попыткой. Повторное применение должно быть явным или ограниченно автоматическим; закрытие не должно молча считать draft сохранённым. Приёмка: временная ошибка, затем успешная повторная попытка; новый draft во время failed await; закрытие после ошибки.

### R4. P2 — документированная упаковка ZIP зависит от файла, отсутствующего в чистом клоне

Места: `scripts/package.ps1:40`; `.gitignore:8`; `docs/development/BUILD.md`.

`package.ps1` безусловно копирует `docs/STATUS.md` при `$ErrorActionPreference='Stop'`. Файл существует локально, но исключён из Git и не отслеживается (`git ls-files docs/STATUS.md` пуст). Сборка ZIP по опубликованной инструкции на чистом клоне упадёт на этой строке после publish и копирования зависимостей.

Доказательство: проверены скрипт, ignore и состав Git. Полный чистый clone/package с повторным скачиванием драйверов не выполнялся; ранее документированное ограничение EXE на сохранённый native baseline — отдельная проблема и не используется как доказательство этого дефекта.

Исправление: генерировать публичный статус из отслеживаемых данных либо убрать обязательную зависимость от локального STATUS. Проверять обязательные входные файлы до дорогой сборки. Приёмка: ZIP из чистого checkout после получения документированных зависимостей.

### R5. P2 — обновления неограниченно накапливают полные копии приложения

Места: `installer/Install.ps1:81–82, 120–121, 171`; `installer/Uninstall.ps1`.

Каждое успешное обновление оставляет отдельную `.backup-<guid>` со всем self-contained runtime. Лимита количества/возраста, доступного пользователю управления откатом и очистки собственных backup при удалении нет. Это полезное сохранение отката, но неограниченное накопление расходует диск на каждой установке.

Измерено на этом ПК: активная установка 176,53 МиБ; четыре backup по 176,52 МиБ, суммарно около 706,08 МиБ дополнительно. Они не удалялись. Инвентаризация: `installed-storage.json`.

Исправление: формализовать реестр собственных backup и хранить одну предыдущую подтверждённую версию либо предложить пользователю управляемую очистку. Удаление ограничить проверенными owned-файлами; сохранять посторонние/изменённые файлы, не применять широкую маску DS5Link*.

### R6. P2 — очередь отложенных USB/IP-ответов не имеет общего лимита

Места: `engine/vds/src/platform/win32/vds_usbip.cc:665–669, 1180–1186, 1713–1742`.

Проверяется размер одного transfer и количество ISO-пакетов, но `paced_replies` растёт без ограничения количества записей, байтов или горизонта времени. Каждый следующий ISO-запрос продвигает anchor ещё на `number_of_packets` миллисекунд. Импортировавший порт клиент, отправляющий быстрее реального времени, может накапливать память и ответы на далёкое будущее. Ограничение обычной HID-очереди до 8 элементов этого не исправляет.

Доказательство статическое. Штатный USB/IP-драйвер обычно ограничивает число незавершённых URB; замечание относится к некорректному/враждебному импортированному клиенту. Listener привязан к loopback, поэтому это не утверждение об удалённой атаке из сети. Захват порта и нагрузочная атака на рабочую службу не запускались.

Исправление: лимиты outstanding requests/bytes и максимального времени до due, корректный отказ/разрыв при превышении; отдельная проверка отмены URB. Приёмка: изолированный импортированный клиент с burst ISO и медленным чтением, память ограничена, штатный аудиопоток не теряет ответы.

## Оптимизация размера: измеренные варианты

Все размеры в МиБ (2^20 байт), не в десятичных МБ.

| Объект | Размер | Что входит |
|---|---:|---|
| Текущий Setup.exe 0.1.28 | 109,263 | Bootstrap, сжатое приложение, три драйверных установщика |
| Текущий payload/app | 176,409 | .NET, UI, native engine, CRT, лицензии; 496 файлов |
| Чистый publish, self-contained | 173,333 | Только выход dotnet publish; без engine и дополнительных лицензий |
| Тот же publish, SatelliteResourceLanguages=ru | 157,867 | Русские и нейтральные ресурсы; 271 файл |
| Framework-dependent UI | 2,316 | Код UI и NAudio, без .NET runtime и native engine |
| Native vdsd.exe | 0,742 | Сам движок |
| Три установщика драйверов до упаковки | 38,567 | USBip, HidHide, ViGEmBus |

**Первое простое сокращение — языковые ресурсы.** Пробный publish с `-p:SatelliteResourceLanguages=ru` убрал 204 файла и 15,466 МиБ относительно такого же чистого self-contained publish. Эти же 204 файла занимают 5,355 МиБ сжатых данных в текущем payload.zip. Ожидаемый размер app с прежними engine/лицензиями — около 160,94 МиБ; окончательный EXE с этой настройкой ещё не собирался. Это штатная настройка SDK: [Microsoft, SatelliteResourceLanguages](https://learn.microsoft.com/en-us/dotnet/core/project-sdk/msbuild-props#satelliteresourcelanguages).

Рендер главного окна из publish-ru и framework-dependent сборок завершился успешно; PNG совпали по SHA-256. Это проверка загрузки и одного синтетического рендера на текущем ПК, не полная приёмка локализаций, всех диалогов, звука и установщика. При внедрении нужны также settings/tray/diagnostics/ошибки runtime на чистой Windows.

**Самый большой выигрыш требует выбора модели распространения.** Framework-dependent UI составляет 2,316 МиБ; вместе с существующим engine/лицензиями app был бы примерно 5,4 МиБ. Но потребуется отдельно установленный совместимый Windows Desktop Runtime x64. Если его нет, загрузка/установка runtime остаётся расходом пользователя; это не превращает полный автономный установщик в 5 МиБ. Различие моделей: [Microsoft, publishing modes](https://learn.microsoft.com/en-us/dotnet/core/deploying/).

**Самый большой уже накопленный расход — backup.** Ограничение хранения старых собственных версий здесь потенциально важнее сокращения DLL. Автоматическое удаление существующих копий в рамках ревью не проводилось.

**Второстепенные возможности:** удалить PDB из пользовательского пакета, оставив отдельные symbols (~66 КиБ для UI); проверить фактически необходимые CRT DLL вместо копирования всех `*.dll`; рассмотреть отдельный небольшой updater при сохранении полного offline setup. У каждого драйверного обновления должна остаться проверка версии, подписи и хеша. Простое удаление runtime DLL «по виду» не предлагается.

**Не включать PublishTrimmed вслепую.** Для WPF/WinForms trimming официально ограничен/отключён из-за несовместимостей; текущий UI использует оба стека. NativeAOT не рассматривается как простой флаг уменьшения существующего WPF-приложения. [Microsoft, known trimming incompatibilities](https://learn.microsoft.com/dotnet/core/deploying/trimming/incompatibilities).

## Оптимизация CPU, задержек и кода

1. **Снизить служебную работу ручных эффектов.** `EffectsRuntime.cs:6` задаёт период 10 мс даже для одного постоянного цвета LED, в Paused и без audio. Каждая попытка создаёт новое pipe-соединение и JSON (`BridgeClient.cs:47–65`); сервер создаёт отдельный watchdog-поток для FlushFileBuffers (`vdsd.cc:2687–2697`). Потенциально это до ~100 соединений и короткоживущих потоков в секунду, фактическая частота зависит от dispatcher/IPC. Разделить heartbeat эффектов (~100–150 мс с запасом к lease 500 мс), аудиокадры и отображение статуса; использовать долгоживущее соединение/согласованный batch-протокол. При Paused не посылать high-rate audio. Ускорение CPU ещё не измерено, это кандидат для A/B.

2. **Сначала исправить длительные блокировки, затем сокращать буферы.** Для native audio заданы 24 блока priming, 48 fresh, максимум 64, ожидание priming до 300 мс (`vdsd.cc:82–95`). Это основание измерить возраст аудиоблоков и end-to-end задержку, а не заявление, что сейчас измерены 300 мс задержки. `ds5link_audio_queue.hh` с timestamp/trim существует, но не подключён к производственному тракту: поиск использований в `engine/vds/src` находит только его определения. Его unit-test не доказывает ограничение возраста реальной очереди. Нужны timestamps enqueue/dequeue/write, p50/p95/p99, underflow/drop и игровой A/B перед изменением принятых буферов.

3. **Убрать повторные выделения в горячих путях после профилирования.** UI создаёт массивы HapticFrame/JSON; transport создаёт vectors и Win32 events на операции; микрофонный буфер удаляет префикс vector. Подходящие кандидаты: переиспользуемые буферы/OVERLAPPED events и настоящий ring buffer. Не менять lifetime overlapped-буфера до завершения CancelIoEx/дренирования. Native бинарник уже собран с /O2 и занимает меньше 1 МиБ, поэтому переписывание DSP ради размера EXE имеет низкий приоритет.

4. **Разделить ответственность крупных исходников.** Windows `vdsd.cc` — 3493 строки, `vds_usbip.cc` — 1855, `vds_bt.cc` — 1252. Выделить ControlPipeServer, supervisor, PS5/Xbox/USB session lifecycle и audio scheduler; заменить глобальные runtime-singleton состояния объектами с явным lifetime. Для новых компактных заголовков/C# восстановить обычное форматирование: несколько переходов состояний в одной строке затрудняют поиск ошибок R2/R3. Это улучшение проверяемости; обещать ускорение или меньший EXE от одного разбиения нельзя.

5. **Убрать лишние пробуждения на паузе.** `TimerResolutionGuard(1 ms)` живёт на протяжении всей службы (`vdsd.cc:3395`), включая Paused. Запрашивать точность таймера на период активной сессии и проверять потребление/латентность после изменения. Это второстепенно относительно блокировок и high-rate IPC.

Короткое наблюдение текущей службы: Paused, UI не запущен; 10 интервальных выборок дали среднюю CPU ~0,067% от общей мощности процессоров, максимум ~0,191%; working set около 10,1 МиБ, private bytes около 1,83 МиБ. Сборщик сам делает IPC/CIM и влияет на замер. Эти цифры не характеризуют активную игру, WPF или audio capture; выводов об их расходе по idle-прогону нет.

## Проверки и ограничения

- `scripts/build.ps1` — успешно; WPF 0 предупреждений, 0 ошибок.
- `scripts/test.ps1` — 13/13 native, 54 managed, 48 synthetic UI-сценариев, mock-проверки зависимостей и 21 ownership-removal check.
- `git apply --reverse --check` для текущего патча движка — успешно.
- Изолированный `probe/Probe.csproj` воспроизвёл R2 и R3; использовал preview-окно без отображения, неверный endpoint и делегат с искусственной ошибкой. Рабочий pipe не использовался.
- Три publish-варианта собраны; два проверены через `--render-preview`. Изменения сборочных параметров не внесены в csproj или релизные скрипты.
- Получены размеры релиза, backup и короткая read-only статистика службы. Служба наблюдалась Paused и не переключалась.
- Не выполнялись установка/удаление, UAC lifecycle, захват USB/IP-порта, отключение устройств, аварийное завершение рабочей службы, физический sleep/resume или игровая проверка. Нет заключения о физической latency/приёмке всех функций.
- Метаданные локального релиза 0.1.28 сохраняют `candidate=true`, `hardwareAccepted=false`.
